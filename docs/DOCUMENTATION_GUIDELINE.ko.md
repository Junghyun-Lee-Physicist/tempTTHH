# 문서화 가이드라인 — 비동기 다중 에이전트(사람 + AI) 프로젝트

> **성격:** 읽기용 한국어판 (사람이 읽는 용도) · **정본(canonical):** `DOCUMENTATION_GUIDELINE.en.md` (툴에 프롬프트로 주는 영어판 — 항상 동기화) · **범위:** 프로젝트 무관(project-agnostic). 어느 repo에든 "문서화 계약"으로 넣어 사용.

## 0. 먼저 읽을 것 (목적)

이 프로젝트는 **여러 사람과 여러 AI 툴이, 서로 다른 쓰레드(thread)와 서로 다른 시간대에서, 기억을 공유하지 않은 채** 작업합니다. 문서는 "이 프로젝트가 무엇이고, 왜 지금처럼 만들어졌으며, 현재 어디까지 와 있는지"에 대한 **유일하게 공유되는 영속적 진실의 원천(single source of truth)** 입니다.

이 가이드라인은, **아무 사전 맥락 없이 시작하는 임의의 에이전트(사람이든 AI든)가 (1) 문서만으로 정확한 프로젝트 상태를 복원할 수 있고, (2) 다음 사람을 위해 문서를 정확한 상태로 남기도록** 문서를 쓰고 관리하는 방법을 규정합니다. 권고가 아니라 계약으로 취급하십시오.

**모든 문서의 합격 기준:** *유능한 외부인, 혹은 갓 시작한 AI 쓰레드가, 원저자에게 묻지 않고 문서만으로 이 작업을 이어받을 수 있는가?* 아니라면 그 문서는 불완전합니다.

## 1. 왜 문서를 쓰는가

- **문서는 프로젝트의 기억이다.** 쓰레드별·사람별 기억은 사적이고 일시적이지만, 문서는 공유되고 영속적입니다. 문서에 없으면, 다음 에이전트에게는 존재하지 않는 것입니다.
- **공유되는 "우리"는 없다.** 다른 시간대의 협업자는 그 대화에 없었고, 새 쓰레드의 AI는 이전 쓰레드를 전혀 기억하지 못합니다. 독자가 당신의 맥락을 공유한다고 가정하고 쓰지 마십시오.
- **문서는 상태·결정·근거를 담는다** — 코드가 무엇을 하는지뿐 아니라, *왜 지금처럼 되어 있고, 무엇을 시도했고, 무엇을 기각했으며, 무엇이 확정이고, 무엇이 아직 미정인지.*

## 2. 문서에서 항상 복원 가능해야 하는 것

1. **무엇이 존재하는가** — 구성요소와 각각의 용도.
2. **왜 지금처럼인가** — 설계 뒤의 근거와 제약.
3. **무엇이 진행 중인가** — 현재 상태, 다음 단계, 미해결 질문.
4. **무엇이 확정 vs 미정인가** — (근거가 달린) 확정 결정과, 제안·미지를 명확히 분리.
5. **무엇을 건드리면 안 되는가** — 불변식(invariant)과, 그것이 왜 핵심인지.

## 3. 문서 세트 (구조)

**진입점 — 인덱스(`README`).** 지도 역할: 어떤 문서가 있고 각각 언제 읽는지. 사람이든 AI든 모든 독자는 여기서 시작합니다.

**문서 하나, 역할 하나.** 각 문서는 단일한 *목적·독자·변경 축(change-axis)* 을 가집니다. 한 파일에 여러 관심사를 섞지 마십시오(합칠지 나눌지 판단은 §7).

**표준 문서 유형:**

| 유형 | 답하는 질문 | 언제 바뀌나 |
|---|---|---|
| 인덱스 / README | "여기 뭐가 있고 어디서 시작하나?" | 문서 세트가 바뀔 때 |
| 목적 & 근거 | "이건 무엇을 위한 것이고 왜인가?" | 목표/전략이 바뀔 때 |
| 아키텍처 | "어떻게 만들어졌고 어떻게 확장하나?" | 구조가 바뀔 때 |
| 레퍼런스(구성요소별) | "X는 정확히 어떻게 동작/입출력하나?" | 그 구성요소가 바뀔 때 |
| **변경 로그(Changelog, 추가 전용)** | "무엇이 언제 바뀌었나?" | 매 변경마다 |
| **결정 로그(Decision log)** | "왜 이 선택? 다른 후보는? 아직 유효한가?" | 결정이 내려지거나 대체될 때 |
| **상태 / 진행(Status)** | "지금 우리는 어디인가?" | 상시 |
| 트러블슈팅 / 인시던트 | "이게 깨졌다 — 원인과 해결?" | 문제가 해결될 때 |
| 기여 규칙 | "어떻게 안전하게 바꾸나?" | 프로세스가 바뀔 때 |

**모든 문서의 머리말에 담을 것:** 한 줄 목적, 대상 독자, 상태 + 마지막 의미있는 갱신일, 관련 문서 링크.

## 4. 문서를 어떻게 쓰는가 (사람·AI 입력으로 작동하도록)

- **결론 먼저(BLUF, Bottom Line Up Front).** 가장 중요한 사실/결론을 맨 앞에, 세부는 뒤에.
- **사전 맥락 0을 가정하고 써라.** "앞서 논의한 대로", 암묵적 "우리", 말 안 한 가정 금지. 다음 독자는 그 자리에 없었습니다.
- **상태를 명시 라벨로.** 고정 어휘 사용 — **DECIDED / PROPOSED / OPEN / DEPRECATED** — 그리고 날짜. 라벨·날짜 없는 서술은 비동기 독자에게 모호합니다.
- **사실 하나는 한 곳에만.** 각 사실은 한 번만 쓰고 다른 곳에선 링크. 중복은 어긋나서(drift) 거짓이 됩니다.
- **안정적이고 서술적인 헤딩.** 정확히 링크·인용 가능하도록("§X 참조"가 계속 같은 뜻이도록).
- **암시하지 말고 보여줘라.** 실제 명령어·브랜치명·코드·값을 넣되, 그에 대한 설명만 적지 말 것.
- **훑기 쉽게 + 빠짐없이.** 스캔용 헤딩·짧은 단락, 그러나 필요한 사람에겐 빠진 단계가 없도록.
- **용어는 한 번 정의**하고 일관되게 사용.

## 5. 어떻게 개발하는가 (워크플로)

1. **무엇이든 바꾸기 전에 관련 문서를 읽어라.** 그것이 당신의 맥락입니다. (AI 쓰레드: 무엇을 읽었는지 밝히기.)
2. **변경할 때마다 즉시 changelog에 기록하라** — 나중에·한꺼번에가 아니라.
3. **결정할 때마다** decision log에 기록: 선택·근거·검토한 대안·상태.
4. **문제와 해결을 매번** 트러블슈팅에 기록: 증상 → 원인 → 해결.
5. **상태 문서를 최신으로 유지하라.** 임의의 에이전트가 "지금 어디?"를 확인하는 단일 지점.
6. **DECIDED 항목을 말없이 다시 열지 말고, PROPOSED를 확정으로 취급하지 마라.** 결정에 이의가 있으면 상태를 명시적으로 바꾸고 이유를 적을 것.
7. **변경은 작고 읽히게,** 각각 명시된 이유에 묶어서.
8. **세션 종료 시 — 멈추기 전에 문서를 갱신하라.** 무엇이 바뀌었는지 요약하고 영향받은 문서에 반영. AI 쓰레드엔 필수: 쓰레드 내 기억은 다음 쓰레드로 넘어가지 않습니다. 오직 문서만 넘어갑니다.

## 6. AI 에이전트 전용 규칙

- **너는 다른 쓰레드의 기억이 전혀 없는 상태로 시작한다.** 문서가 너의 유일한 신뢰 가능한 맥락이다. 행동 전에 읽고, 문서가 확립하지 않은 상태를 가정하지 마라.
- **상태를 지어내지 마라.** 문서가 침묵하면 그것은 확립되지 않은 것 — 알아내거나 **OPEN**으로 표시하고 물어라. 가정을 확정 사실로 제시하지 마라.
- **뉘앙스를 보존하라.** 사람의 결정을 기록할 땐 충실히(중요하면 원문 인용) 담고, 뉘앙스를 의역으로 날리지 마라.
- **문서를 이어갈 수 있는 상태로 남겨라.** 작업 완료에는 "다음 에이전트가 너 없이 이어갈 수 있는 상태로 문서를 남기는 것"이 포함된다. 덤이 아니라 작업의 일부다.
- **확정 여부가 불확실하면** decision log를 확인하고, 거기에 없으면 **OPEN**으로 취급하라.

## 7. 합칠까 나눌까? (재사용 가능한 판단 기준)

**두 문서는 "같은 작업에서 함께 읽히고 + 함께 바뀔 때"만 합쳐라. 아니면 분리하고, 맞닿는 지점에서 교차링크하라.**

- "왜"(목적/물리/제품 근거)와 "어떻게"(아키텍처/엔지니어링)는 보통 **독자가 다르고 변경 축이 다르므로** 기본은 **분리** 문서이고, 왜가 어떻게를 제약하는 곳에서 링크합니다.
- 단일 통합 문서는 **좁은 스코프**(예: 작은 모듈 하나)에서 why/how가 짧고 결합되어 늘 함께 읽힐 때만 정당화됩니다.
