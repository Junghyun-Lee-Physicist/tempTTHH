# 계획: v15 ntuple 로 analyzer 돌리기 (2024 먼저 — 2026-10-02 결정; 첫 안은 2018UL 먼저) 와 연도별 한 명령 workflow

> **목적:** NtupleForge 가 만든 2018UL·2024 v15 ntuple 로 이 analyzer 의 전체 사슬(prescan → stitch → btagtrig → trigger SF → b-tag
> norm reweight → main → plot)을 돌리기 위해 무엇을 어떤 순서로 고치고 돌리는지. 생산이 다 끝났을 때 "한 명령을 다시 치기만 하면"
> 되도록 만드는 설계를 포함한다.
> **대상 독자:** 이 분석을 이어받는 사람과 AI 세션(사전 맥락 없음).
> **상태:** **PROPOSED** (2026-10-01, AI 작성; 사용자 요청 "failed job 기다리면서 이미 생성된 것으로 analyzer 동작시키자. full workflow 갖춰
> 놓으면 나중에 다 되었을때 돌리기만 하면 되니까. 일단 계획만 잡자"). 결정이 필요한 항목은 §7, 그 전에는 코드를 바꾸지 않는다.
> **2026-10-02:** 사용자 결정으로 **2024 가 첫 대상**(D-2026-10-02-A). 단계와 통과 기준은 **§9**(새)가 정하고 §5 의 순서를 대체한다.
> 같은 날의 결정: eventBuffer 재생성 정책(D-2026-10-02-B, §7 D7 을 대체), 연도별 event cleaning 표(D-2026-10-02-C, §9.2), N0~N8 의 답(D-2026-10-02-D),
> blinding(D-2026-10-02-E, PROPOSED). §1~§8 은 10-01 의 조사로 그대로 둔다.
> **관련:** 현재 상태 [`STATUS.md`](STATUS.md)(OPEN 6 = 2018UL 대응), 2017 절차 [`RUNBOOK_2017_SF_rederive.md`](RUNBOOK_2017_SF_rederive.md),

## 0. 결론 먼저

- **2026-10-02: 2024 먼저.** 아래의 "2018UL 이 첫 대상이다" 는 대체되었다(D-2026-10-02-A). 단계·통과 기준·연도별 event cleaning 은 §9.
- **지금의 analyzer 는 v15 ntuple 에서 돌릴 수 없다. 대부분이 크래시가 아니라 무증상 오답이다.** v15 에 `Jet_jetId`·`Jet_puId` 가 없어
  모든 jet 이 jet ID 에서 떨어지고(0 event), rho·MET·electron ID 는 이름이 바뀌어 0 으로 읽힌다(§2). 파일 목록은 CRAB 의 `failed/`
  사본까지 넣고, 출력 디렉터리에 연도가 없어 2017 출력을 덮어쓴다. 그래서 **코드가 먼저**다(§4 의 A0~A2).
- **2018UL 이 첫 대상이다.** 생산이 끝났고(MC 2,277/2,277, Data 1,466/1,466), Data 는 KNU 집계 PASS(원장 V55)다. 2024 는 생산이
  95 % 쯤이고(10-01: MC 18,536 + Data 7,400 done, fail 576 + 404), 연도 설정(A4)·skim 용 prescan(A5)·결정(§7 D4~D8)이 더 필요하다.
- **처음 돌릴 수 있는 단계는 2018 prescan 이다.** prescan 은 `genWeight`·`genTtbarId`·run/lumi/event 와 `Runs` tree 만 읽어 v15 의
  스키마 문제를 타지 않는다. A0(빌드) + A2(연도 디렉터리, 새 파일 목록, 2018 yml·json)만 있으면 되고, 그동안 A1(스키마)을 쓴다.
- **workflow 의 뼈대**: 연도마다 상태 디렉터리, **dataset 단위 완료 판정**(NtupleForge 집계가 DAS 와 맞는 dataset 만 S 트랙에;
  docs/12 §5.4), 샘플마다 **고정된 파일 목록(snapshot)** 을 prescan·btagtrig·main 이 함께 쓰는 규칙(정규화가 제출 때의 상수이기 때문, §3 3),
  단계마다 입력 hash 로 건너뛰기, 그리고 `tools/run_year.py --year <Y>` 하나를 끝날 때까지 다시 치는 방식(§6).

## 3. 설계 원칙 (PROPOSED)

1. **연도마다 상태를 나눈다.** `AnalyzerOutput/<year>/<mode><suffix>/`, `condor/<year>/...`, `filelists/<year>/`, `prescan_summary/<year>/`,
   `DerivedCorr/<kind>/<year>/`. 2017 의 기존 위치는 그대로 두고 2017 도 새 규칙으로 다시 낼 수 있게만 한다.
2. **dataset 단위 완료 판정.** NtupleForge `script/forge_campaign_audit.py` 의 결과(D1 출력 수와 job 번호, D3 입력 하나에 한 행, D4 Σ`n_in`
   또는 Σ`Events` = DAS)가 PASS 인 dataset 만 COMPLETE. 나머지는 PARTIAL 로 표시하고 workflow 시험에만 쓴다(NtupleForge docs/12 §5.4:
   부분 생산으로 plot 을 그리지 않는다). Data 는 era 단위로 COMPLETE 이면 그 era 의 lumi 만 더한다.
3. **샘플마다 고정된 파일 목록(snapshot).** 목록과 그 hash 를 한 번 만들고, prescan·btagtrig·main 은 같은 snapshot 을 쓴다. snapshot 이
   바뀌면(새 파일) 그 샘플의 prescan 부터 다시 한다. 이유: MC 의 base weight 는 제출 때 `prescan_summary` 의 Σ`genEventSumw` 로 만든 상수이고
   main 은 자기 입력의 `Runs` 를 읽지 않는다(§2 6). 각 출력에 쓴 weight 와 snapshot hash 를 남겨 merge 에서 한 샘플 안이 같은지 본다.
4. **단계마다 입력 hash → stamp.** 같으면 건너뛴다. stitch·trigger SF·b-tag reweight 처럼 여러 샘플이 얽힌 단계는 그 group 의 샘플이 모두
   COMPLETE 일 때만 돈다.
5. **조용한 0 금지.** 분석이 실제로 쓰는 branch(지금 73 개; NtupleForge `script/check_branchlist.py` 의 `REQUIRED` 와 같고 거기에 쓰지 않는 HLT 하나가 더 있다)를 연도·MC/Data 별
   목록으로 두고 첫 파일에서 하나라도 없으면 FATAL. job 안 파일 사이의 스키마 차이는 파일 목록 단계에서 잡는다(같은 era·같은 스키마끼리만
   한 job).
6. **2017 이 기준이다.** A0 에서 지금 코드로 2017 결과를 먼저 만들어 두고(빌드 첫 확인), 2018/2024 를 위해 바꾼 코드가 2017 에서 같은 결과를
   내는지 매 단계에서 본다(Y1).

## 6. 드라이버: 한 명령 (PROPOSED)

```
python3 tools/run_year.py --year 2018            # 할 수 있는 단계를 하고 멈춘다; 끝날 때까지 다시 친다
python3 tools/run_year.py --year 2018 --dry-run  # 무엇을 할지만
```

단계: `inventory`(A2b) → `prescan`(2018 analyzer prescan / 2024 A5) → `consolidate` → `stitch` → `btagtrig` → `merge_btagtrig` → `trigsf`
→ `btagrw` → `main` → `merge_main` → `plot`. 단계마다 `state/<year>/<stage>.json` 에 입력 hash, 출력, 상태를 적는다.

- 한 줄 요약: `RUN|<year>|<stage>|DONE|SKIP|WAIT n/m|BLOCKED <이유>|FAIL <이유>`, 끝에 다음에 할 일 한 줄.
- condor 단계는 제출하고 바로 끝난다(기다리지 않는다); 다음 실행이 끝 표시(`prescan` 1 행 tree, `cutflow_w_full`)로 완료를 보고 남은 것만 다시 낸다.
  끝 표시가 없는데 condor 에 아직 있는 job 은 다시 내지 않는다(`condor_q` 확인).
- group 단계(stitch, trigsf, btagrw)는 group 의 snapshot 이 모두 COMPLETE 이고 앞 단계가 DONE 일 때만; 하나라도 바뀌면 그 뒤를 무효로 한다.
- PARTIAL 은 `--allow-partial` 일 때만 쓰고, 그 출력 디렉터리와 plot 에 `PARTIAL` 을 붙인다.
- 실패하면 non-zero exit 와 그 단계의 첫 오류 줄(분석기 exit code 는 `reference/ERROR_CODES.md`).

### 9.5 QCD 비교의 정의 (Stage 8, 9)

영역 R ∈ {FH, μCR, eCR}, cut 단계 s (7 = HT > 500, 8 = nb ≥ 2, 그리고 nb ≥ 3, nb ≥ 4), 연도 Y 마다:
- N_data, N_MC(전체), N_QCD(MC, HT bin 합), N_nonQCD = N_MC − N_QCD, 각각의 통계 오차(MC 는 Σw²).
- f_QCD = N_QCD / N_MC; Data/MC = N_data / N_MC; k_QCD = (N_data − N_nonQCD) / N_QCD (QCD 를 몇 배 하면 Data 와 맞는가).
- 억제: f_QCD(μCR) / f_QCD(FH), f_QCD(eCR) / f_QCD(FH).
- 연도 비교 (Stage 9): (Data/MC)_2024 / (Data/MC)_2017 를 영역·단계마다, 그리고 같은 비를 분포(HT, nb, 6 번째 jet pT)로 그린 ratio plot.
- 함께 적을 것: lepton SF 를 쓰지 않았으므로(N4) lepton CR 의 non-QCD MC 정규화가 lepton 하나당 몇 % 어긋날 수 있다(크기는 POG SF 로 한 번
  재서 표에 적는다); 2024 에 W→ℓν·DY 표본이 없으면 N_nonQCD 가 작아져 k_QCD 가 커 보인다(D13).
